# 航电密钥轮换复核台

在密钥轮换演练中，穷尽两枚独立安全模块之间**保持控制端发起顺序**的消息投递、
断电与恢复交织，回答一个安全问题：

> 两枚模块会不会**共同确认一份由不同纪元密钥签出的发布令**？

发现违约时给出**动作数最短**、同长度按 **（模块, 指令标识, 事件类型）** 稳定排序的
完整交织，并逐步展示双模块的规范状态；安全时给出已覆盖状态摘要。

录入指令后还可追加**现场事件前缀**（至多 8 步）：把已观察到的投递 / 落盘 / 确认 /
断电 / 恢复逐步归约到双模块状态，再继续穷尽尚未发生的交织，回答
“事已至此，剩余交织是否仍可能导致跨纪元共同确认”。

全部计算在浏览器 **Web Worker** 中完成；服务端为零第三方依赖的 Node 静态服务。

## 复核模型

### 指令（每行一条，按控制端发起顺序，至多 16 条）

| 指令 | 含义 |
| --- | --- |
| `prepare <模块> <密钥指纹>` | 准备（持久暂存）一枚纪元密钥，亦可用 `旧`/`新` 代指 |
| `activate <模块>` | 将已暂存密钥提交为持久纪元 |
| `issue <模块> <发布标识>` | 以当前持久纪元密钥确认一份发布令 |
| `recover <模块>` | 断电恢复：**仅重放已落盘记录** |

亦支持中文助记符 `准备 / 激活 / 签发 / 恢复`。

### 现场事件前缀（可选，每行一步，至多 8 步）

| 前缀步骤 | 归约为 |
| --- | --- |
| `投递 <模块> #n` | 指令 #n 投递到模块 |
| `落盘 <模块> #n` | 指令 #n 完成持久写入（恢复指令的落盘重放须写作「恢复」） |
| `确认 <模块> #n` | 指令 #n 的确认到达（含恢复后到达的迟到/重复确认） |
| `断电 <模块> #n` | 指令 #n 在途期间断电，按所处阶段归约为写入前 / 写入后确认前断电 |
| `恢复 <模块> #n` | 恢复指令 #n 落盘重放，模块回到在线 |

`#n` 为指令的控制端发起顺序编号（从 #0 起）。前缀是已观察到的现场记录，
**不作为新的控制端指令**：复核先按既有持久化语义逐步归约前缀——任一步在当前
双模块状态下不可能发生时，稳定定位**首个不合法步骤**并清除旧结论；随后从所得
双模块状态继续穷尽尚未发生的交织。前缀自身已形成违约时，完整见证自前缀起展示；
否则保留最短且稳定排序的后续反例或安全覆盖摘要。

### 指令生命周期与三个断电点

```
投递 ──► 持久写入 ──► 确认
          │            │
  ①写入前断电     ②写入后确认前断电      ③确认后断电
  （未落盘，丢失） （已落盘，确认迟到）   （记录已生效）
```

* ①恢复时不重放（没有落盘记录）；
* ②恢复后重放落盘记录，**迟到/重复确认不改变模块记录**（穷举中显式枚举该事件）；
* ③记录保持生效。

### 规范状态与穷举

每个模块的规范状态仅由三部分构成：

* 持久纪元（未激活 / 旧 / 新）
* 准备密钥
* 已确认发布集合（`发布标识 → 旧/新密钥位掩码`）

搜索按层 BFS 穷尽所有合法交织：

* 每个模块一条 FIFO 通道，严格保持控制端对该模块的发起顺序；
* 等价前缀（同调度位置 + 同规范状态）合并；
* 首次出现违约的层即**最短动作数**层，层内按（模块, 指令序号, 事件）字典序取最小见证；
* 违约判据：同一发布标识被两模块以**不一致的纪元密钥位掩码**确认。
  两模块均以同一纪元密钥确认（掩码相同）为安全；未持久激活时签发不成立。

实测 16 条指令、含多次恢复的最坏安全形态约 1.8 万状态、70ms 量级完成。

## 本地运行（无需 Docker）

要求 Node ≥ 20，零依赖安装：

```bash
npm start                 # 默认 http://localhost:8080，健康响应 GET /healthz
PORT=9090 npm start       # 自定义端口
```

复核：填入旧/新密钥指纹、两个模块的持久初态（持久纪元、准备密钥、已确认发布）、
指令序列，可再追加现场事件前缀，点击 **复核**。点击 **清空草稿与结论** 会同时清空
输入与旧结论；任何校验失败也会一次性指出并清除旧结论。修改密钥、初态、指令或
现场前缀后，旧结论立即清除，需重新复核；未填写前缀时结论与指令语义保持不变。

一次性校验（核心状态测试 → 静态构建检查 → Worker 运行时冒烟 → HTTP 冒烟，
退出码结束）：

```bash
npm test                  # 仅核心状态测试
npm run verify            # 完整 verify 流程；成功 0，失败 1
```

## Docker Compose

宿主端口可配置（默认 8080）：

```bash
HOST_PORT=9090 docker compose up -d web
curl -s http://localhost:9090/healthz
```

verify 服务围绕本轮换场景运行核心状态测试、静态构建检查和页面及健康地址的
HTTP 冒烟，**完成后以退出码结束**：

```bash
docker compose run --rm verify    # 退出码 0 全部通过，1 存在失败
```

## 目录结构

```
src/core.mjs     规范状态模型、解析校验、现场前缀归约、穷尽搜索（Worker 与 Node 测试共用）
src/server.mjs   零依赖静态服务（/ 操作入口，/healthz 健康响应）
src/verify.mjs   verify 编排：测试 → 构建检查 → Worker 冒烟 → HTTP 冒烟
web/index.html   操作页面
web/app.js       前端：草稿收集、Worker 调度、结论/见证渲染
web/worker.mjs  Web Worker 入口
test/core.test.mjs 核心状态测试（24 组，含现场前缀归约 / 非法前缀 / 无前缀兼容）
```
